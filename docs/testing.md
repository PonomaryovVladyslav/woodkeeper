# Woodkeeper — план тестирования

> Этап 3: проектирование. Дата: 2026-10-16. Модель данных и API — см. [data-model.md](data-model.md).

## 1. Уровни и инструменты

| Уровень | Что проверяем | Инструменты |
|---|---|---|
| Бэкенд: unit | Схемы, валидация, маппер `faces` ↔ колонки, подпись cookie | pytest |
| Бэкенд: API | Все эндпоинты через HTTP, права доступа, БД | pytest + FastAPI `TestClient` (httpx) |
| Бэкенд: миграции | Alembic совпадает с моделями, upgrade/downgrade | pytest + Alembic API |
| Фронтенд: unit | Чистая логика в `lib/` | Vitest |
| Фронтенд: компоненты | Формы, списки, фильтры, подтверждения | Vitest + React Testing Library + MSW (мок API) |
| E2E | Ключевые сценарии в настоящем браузере на настоящем бэкенде | Playwright |
| Ручное | Реальный вход Google, 3D-взаимодействие, телефон | Чек-лист (раздел 6) |
| Статический анализ | Стиль, типы | ruff, mypy; tsc, oxlint |

Покрытие — ориентир, а не цель: бэкенд ~90%, фронтенд — вся логика в `lib/` и ключевые компоненты.

## 2. Тестовое окружение бэкенда

- **БД:** для каждого теста — отдельная SQLite во временном файле (`tmp_path`), создаётся через тот же `engine`-код, что в проде, чтобы срабатывали `PRAGMA foreign_keys=ON` и CHECK-ограничения. In-memory не используем — проще получить расхождение с продом.
- **Google:** `verify_google_token` подменяется через `app.dependency_overrides` / monkeypatch; возвращает заранее заданные `sub`, `email`, `name`. Сеть в тестах не используется.
- **Фикстуры** (`tests/conftest.py`):
  - `client` — неавторизованный клиент;
  - `user_client` — авторизованный пользователь A;
  - `other_client` — авторизованный пользователь B (для проверок чужого доступа);
  - `make_project(...)`, `make_board(...)` — простые функции-фабрики (без factory_boy).

Структура:

```
backend/tests/
  conftest.py
  test_schemas.py       валидация, нормализация цвета, маппер faces
  test_auth.py
  test_projects.py
  test_boards.py
  test_access.py        доступ к чужим данным
  test_db.py            PRAGMA, CHECK, каскады на уровне БД
  test_migrations.py
  test_static.py        SPA-fallback, кэш-заголовки, /api/config
  test_backup.py        app.backup
```

## 5. E2E (Playwright)

### Вход в тестах

Реальный Google-вход автоматизировать нельзя. В бэкенде есть эндпоинт `POST /api/auth/test-login`, который регистрируется **только при `APP_ENV=test`**. Отдельный backend-тест проверяет, что при `APP_ENV=production` маршрута не существует (404).

### Окружение

Playwright (`frontend/playwright.config.ts`) поднимает бэкенд на `:8001` (`APP_ENV=test`, пустая SQLite `frontend/e2e/.tmp/e2e.db`, `alembic upgrade head`) и production-сборку фронтенда через `vite preview` на `:4173` с прокси `/api` → `:8001`. Каждый тест входит через `test-login` под уникальным пользователем, поэтому тесты изолированы и идут параллельно. Скрипт Google блокируется (`page.route`). WebGL — программный (SwiftShader). Запуск: `npm run e2e`.

### Сценарии

- [x] **Основной путь:** вход → создать подпроект → добавить доску (размеры, количество, 2 облицованные стороны с цветом, заметка) → доска в списке → перезагрузка страницы → данные на месте.
- [x] **Редактирование:** изменить размеры и цвет стороны → изменения видны в карточке.
- [x] **Дублирование:** дублировать → поменять длину → сохранить → в списке две доски, у копии новая длина и «(копия)».
- [x] **Заказ:** отметить «заказана» → доска уходит вниз списка → фильтр «не заказаны» её скрывает.
- [x] **Удаление:** доски и подпроекта с подтверждением.
- [x] **3D-смоук:** редактор открывается, `<canvas>` отрисован, подписи размеров видны, нет ошибок в консоли.
- [x] **3D-клик:** наведение на верхнюю пласть → подсказка, клик → сторона облицована; перетаскивание (вращение) облицовку не переключает.
- [x] **Выход:** после выхода `/` перенаправляет на `/login`.

### Телефон (`e2e/mobile.spec.ts`)

Владелец пользуется приложением в магазине с телефона (Samsung), поэтому отдельные проекты Playwright: **android** — Galaxy S24 (Chromium, 360 px) и **iphone** — iPhone 15 (WebKit, 393 px). Данные заводятся через API («подготовлено дома на ноутбуке»), действия — касаниями.

- [x] Длинные названия подпроекта и доски не вызывают горизонтальной прокрутки.
- [x] Фильтр «Не заказаны» и отметка «Заказана» тапом; бейдж «заказано/всего» не сжимается длинным названием подпроекта; нет горизонтальной прокрутки.
- [x] Редактор на весь экран; шрифт полей ≥ 16 px (иначе iOS зумит страницу при фокусе); цвет в палитре — касаниями, палитра закрывается повторным тапом по образцу; сохранение.
- [x] Тап по грани 3D-модели облицовывает сторону.

Эмуляция не заменяет одну ручную проверку на настоящем телефоне после деплоя (раздел 6).

## 8. CI (GitHub Actions)

На каждый push и pull request:

| Job | Шаги |
|---|---|
| backend | `uv sync` → `ruff check` → `ruff format --check` → `mypy` → `pytest --cov` |
| frontend | `npm ci` → `tsc -b` → `oxlint --deny-warnings` → `vitest run` → `vite build` |
| api-types | Сгенерировать OpenAPI из FastAPI → `openapi-typescript` → `git diff --exit-code` (TS-типы не устарели) |
| e2e | Playwright: desktop (Chromium) + android (Galaxy S24) + iphone (WebKit, iPhone 15); после backend и frontend |
| docker | Сборка образа `linux/amd64` на каждом PR (без push), запуск с `APP_ENV=test`, весь E2E-набор против него |
| release | Только `main`, после зелёного CI: сборка и push образа в GHCR — см. [deploy.md](deploy.md) |

## 9. Порядок внедрения

Тесты пишутся вместе с кодом соответствующей части, а не в конце:

1. Бэкенд: схемы и маппер → `test_schemas.py`.
2. Модели, миграция → `test_db.py`, `test_migrations.py`.
3. Авторизация → `test_auth.py`.
4. Эндпоинты → `test_projects.py`, `test_boards.py`, `test_access.py`.
5. CI для бэкенда.
6. Фронтенд: `lib/` → unit-тесты; компоненты → компонентные тесты.
7. CI для фронтенда и проверка типов API.
8. E2E-сценарии.
9. Ручной чек-лист → деплой → смоук на сервере.
